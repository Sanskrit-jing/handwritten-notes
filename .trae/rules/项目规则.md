# 项目规则：上下文预算、防膨胀与版本控制

> 目标：防止长对话中因上下文超限被截断；约束代码生成行为，禁止补丁式代码膨胀；用 Git 兜底一切可回溯性。
> 核心公式：单次会话占用 = 输入（粘贴内容＋历史对话）＋ 输出（思考＋代码）。
> 本文件位于 `.trae/rules/项目规则.md`，由 Trae 自动加载，同时约束 AI 的输出行为与用户（我）的提问习惯。

## 零、版本控制基线（强制，优先级最高）

1. 项目必须处于 Git 仓库内。若发现项目根目录没有 `.git`：先执行 `git init`，补充 `.gitignore`，完成首次提交后再开始其他任务。
2. `.gitignore` 必备项：`build/`、`.dart_tool/`、`*.exe`、IDE 个人配置、日志与临时文件。
3. 敏感信息（API Key、token、密码、账号）禁止入库。发现疑似敏感文件：先报告，经确认后移出并加入 `.gitignore`，必要时清理历史。
4. AI 未经用户明确确认：不 push、不 force、不改写已推送历史。

## 一、输入控制（约束提问者，AI 可提醒）

1. 用 @ 引用文件、符号或行号，不要整段粘贴源码。
2. 必须粘贴时，只贴：报错信息原文、关键函数、期望行为的描述。
3. 一条消息只提一个任务；多个任务分多条消息或新会话。
4. 不再相关的历史内容，主动说"忽略前面关于 X 的部分"。

## 二、输出控制（约束 AI，硬性要求）

1. 一次只处理当前提出的这一项改动，不扩大范围、不顺手重构。
2. 回答顺序固定：先结论（改了什么、为什么，3 行以内）→ 再细节。
3. 禁止输出：思考过程、备选方案、对需求的复述、与改动无关的解释。
4. 修改长文件时，只输出最小 diff 或改动位置说明，不整文件重写。
5. 无法一步完成的任务，先给"拆步方案（每步一句话）"，等确认再执行。

## 三、会话管理

1. 每完成一个小任务，用固定格式收尾（≤4 行）：做了什么 / 验证结果 / 下一步建议。
2. 单任务完成后建议新开会话，用第六章交接模板带入上下文。
3. 连续对话超过 8 轮（按用户消息数计）仍未完成当前任务时，主动提醒：建议拆步或新开会话。

## 四、长任务执行流程（默认工作方式）

需求 → 拆成单步清单（每步只做一件事）→ 逐条执行 → 每条验证 → 汇总交接。
任何涉及多文件或大范围改动的步骤，执行前先给"文件清单＋方案"并等待确认。

## 五、验证要求（最小验证映射表）

每次改动后只跑与改动相关的范围，不整项目重跑：

| 改动类型 | 最小验证方式 |
|---|---|
| UI / 布局 | `flutter analyze` ＋ 目标页目视检查 |
| 业务逻辑 / 服务 | 对应单测：`flutter test test/xxx_test.dart` |
| 提示词（assets/prompts/） | 对应 pipeline 测试 ＋ 实际调用一次 |
| 依赖 / 全局配置 | `flutter analyze` ＋ 全量 `flutter test` |
| 运行验证 | 按第七章重新编译后启动，禁止旧 exe |

验证失败时：先报告失败现象，再给修复方案，不静默重试多次。

## 六、交接模板（新会话开场用）

```
项目背景：<一句话>
已完成：<上一步结论，3 行内，附 commit 号>
下一步：<明确目标，只写一件事>
关键文件：<路径>
约束：<技术栈 / 风格 / 禁止事项>
```

## 七、编译与运行（Windows，强制）

1. 源码有改动后，运行调试前必须重新编译；禁止直接运行旧 exe。
2. 中文路径会导致 MSBuild 失败，所有构建命令必须走 junction：`C:\n91` → 项目根目录。
3. **日常调试**（改 UI / 快速验证）：

```powershell
Set-Location C:\n91; flutter run -d windows
```

   debug 模式自动编译，支持热重载（r）/ 热重启（R）。

4. **发布 / 验收构建**（先删旧产物，编译失败时旧 exe 不残留，避免误运行旧版本）：

```powershell
Remove-Item "C:\n91\build\windows\x64\runner\Release\novel91.exe" -ErrorAction SilentlyContinue
Set-Location C:\n91; flutter build windows --release
```

5. 运行前核对产物修改时间为本次编译时间，确认无误再启动。

## 八、防补丁式代码膨胀（量化约束）

所有代码修改任务必须遵守，优先级高于普通功能需求。

### 核心原则

1. 修改功能时：优先整块替换旧实现，不局部插入 if、不新增分支、不加兼容开关打补丁。
2. 重写 / 替换一段逻辑，必须删除被替代的旧业务代码，禁止新旧两套逻辑并行。
3. 禁止注释大块旧业务代码；废弃代码直接删除，靠 Git 历史回溯。
4. 禁止新增未使用变量、未使用 import、临时调试日志、无业务意义占位 TODO。

### 量化阈值

- 新增行数 : 删除行数 > 3:1，且本次属于"修改 / 重构"性质（全新功能除外）→ 必须告警，等用户确认才算完成。
- 同一文件同一函数内出现语义重复的新旧两段实现 → 必须告警。

### 改动后强制自检（每轮结束输出，固定 4 行）

```
自检：新增 X 行 / 删除 Y 行
旧逻辑整块替换：是/否（未删除被替换代码时说明原因）
新增兼容 if / 开关 / 重复函数：无（有则说明）
增删比告警：无 / 有（>3:1，待确认）
```

### 禁止清单

- ❌ 为兼容旧逻辑新增 if 开关，造成新旧两套逻辑并存
- ❌ 迭代追加新函数，旧函数保留不删除
- ❌ 遗留调试打印、临时测试代码
- ❌ 保留被注释掉的业务代码块
- ❌ 自行增加额外可配置开关、无要求的预留扩展逻辑

## 九、存量代码审计清理（触发词：清理 / 审计 / 瘦身）

仅当用户明确提出"清理、审计、瘦身"类任务时进入本流程，其余场景不主动全库扫描。

1. **第一步只读审计**：只输出 Markdown 问题清单，禁止修改代码。
   - 分类扫描：注释旧业务代码、调试日志、未使用 import/变量、孤立无调用函数、legacy 兼容 if 分支、重复语义函数。
   - 每条标记风险等级：🟢 低风险 / 🟡 人工复核 / 🔴 禁止删除。
2. **用户确认清单后分批清理**，禁止一次性大范围重构：
   - 批次 1：🟢 低风险项 —— 注释旧代码、调试打印、无用 import
   - 批次 2：🟡 复核通过项 —— 全局无调用废弃函数、废弃变量
   - 批次 3：仅业务确认废弃才执行 —— 旧兼容分支及对应开关；不确定用途一律保留
   - 批次 4：合并重复逻辑，删除重复副本
3. 每一批次：输出 diff → 最小验证 → 单独 commit → 行为确认不变 → 再进下一批。
4. 任何不确定业务用途的代码，绝不擅自删除。

## 十、Git 强制流程

### AI 必须执行

1. 每完成一个任务（或清理的一个批次）且验证通过后，立即 commit，不等用户催促；push 仍需用户确认。
2. commit 消息格式：`<类型>: <中文说明>`。类型：feat / fix / refactor / clean / docs / test / chore。
3. 一次 commit 只包含一个任务（或一个批次）的改动，不混装。
4. 提交前用 `git diff --stat` 核对改动范围，发现无关文件混入先剔除。

### AI 禁止

- ❌ `git push --force` / `--force-with-lease`（除非用户明确要求）
- ❌ 改写已推送历史（rebase / filter-branch）
- ❌ 提交敏感信息、构建产物
- ❌ 验证未通过就 commit

### 回退速查（仅保留高频 6 条）

| 场景 | 命令 |
|---|---|
| 放弃某文件本地修改 | `git restore 文件路径` |
| 查看未提交改动 | `git diff` |
| 撤销上一次提交（保留改动） | `git reset --soft HEAD~1` |
| 撤销已推送提交（安全） | `git revert 提交ID` |
| 查看提交历史 | `git log --oneline` |
| 找历史中删除的代码 | `git log -S "关键词"` |

⚠️ `git reset --hard` 会永久丢弃未提交改动：使用前必须确认已 commit 或已备份，且需用户明确要求。

## 十一、机制真实性红线（真跑通原则）

1. 任何用户可见的功能入口（按钮/面板/开关/流程）必须形成真实闭环：真实状态变更 → 真实落盘或真实外部调用 → 真实回显，三者缺一即视为未完成。
2. 禁止"假完成"形态：模板文案/假数据冒充真实结果；空实现回调、仅提示不改状态；空 catch 静默吞错掩盖断链；依赖永不成立的条件分支。
3. 验收以端到端实际运行为准：真实数据走一遍、查落盘产物、看回显，"代码看起来对"不构成通过。
4. 新增与重构机制一律适用；AI 调用环节至少完成请求构造与响应解析的真实结构验证，关键链路做真实调用抽查。
